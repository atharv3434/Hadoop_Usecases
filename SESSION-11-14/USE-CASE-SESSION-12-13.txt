# Hive Use Case: Online Learning Platform Analytics

## 1. Problem Statement

### Business Scenario

An online learning company offers courses in Python, Big Data, Cloud Computing, Machine Learning, and other technologies.

The company receives three types of data:

* **Learner data** — learner details
* **Course data** — course details
* **Enrollment data** — which learner enrolled in which course

The data engineering team wants to use **Hadoop HDFS and Hive** to build an analytics layer.

The system should be able to:

1. Store learner data in a Hive **internal/managed table**.
2. Store course data in a Hive **external table**.
3. Load data using both:

   * `LOCAL INPATH`
   * HDFS `INPATH`
4. Use different Hive joins to answer business questions:

   * Inner Join
   * Outer Join
   * Map-Side Join
   * Reduce-Side Join
5. Partition enrollment data by year.
6. Query a particular partition efficiently.

### Business Questions

At the end of the project, we should be able to answer:

* Which learner enrolled in which course?
* Which learners have not enrolled in any course?
* Which courses have no learners?
* How many learners are enrolled in each course?
* How can we efficiently join a large enrollment table with a small course table?
* How can partitioning reduce unnecessary data scanning?

# 16. LOCAL INPATH vs HDFS INPATH

This is a very common fresher interview question.

### LOCAL INPATH

```sql
LOAD DATA LOCAL INPATH '/local/path/file.csv'
INTO TABLE table_name;
```

Source:

```text
Local filesystem
```

### HDFS INPATH

```sql
LOAD DATA INPATH '/hdfs/path/file.csv'
INTO TABLE table_name;
```

Source:

```text
HDFS
```

### Simple interview answer

> `LOCAL INPATH` is used when the source file is on the local filesystem, whereas `INPATH` is used when the source file is already stored in HDFS.

# PART H — INNER JOIN

## 18. Find Learner + Course Information

Business requirement:

> Display learners along with the courses they enrolled in.

Run:

```sql
SELECT
    l.learner_id,
    l.learner_name,
    c.course_name,
    e.enrollment_date
FROM learners l
INNER JOIN enrollments_raw e
    ON l.learner_id = e.learner_id

    ON e.course_id = c.course_id;
```

```text
Learners
    |
    | learner_id
    v
Enrollments
    |
    | course_id
    v
Courses
```

### Interview definition

> An inner join returns only records that have matching values in both tables.

# PART J — REDUCE-SIDE JOIN

## 22. What is a Reduce-Side Join?

A normal Hive join can involve:

```text
Mapper
   |
   v
Shuffle
   |
   v
Reducer
   |
   v
Joined result
```

For example:

```sql
SELECT
    l.learner_name,
    e.course_id
FROM learners l
JOIN enrollments_raw e
ON l.learner_id = e.learner_id;
```

Conceptually:

```text
Learner Data             Enrollment Data
     |                         |
   Mapper                    Mapper
     |                         |
     +-----------+-------------+
                 |
              Shuffle
                 |
          Same learner_id
                 |
              Reducer
                 |
             Join Result
```

### Interview answer

> In a reduce-side join, records from both datasets are shuffled according to the join key and brought to reducers, where matching records are joined.

# PART K — MAP-SIDE JOIN

## 23. Business Situation

Suppose the company has:

```text
Enrollment table = very large
Courses table = small
```

For example:

```text
5 TB enrollments
+
10 MB courses
```

It would be inefficient to shuffle both tables.

We can use a **map-side join** when the smaller table can be made available to the mappers.

Run:

```sql
SELECT /*+ MAPJOIN(c) */
    e.enrollment_id,
    e.learner_id,
    c.course_name
FROM enrollments_raw e
JOIN courses c
ON e.course_id = c.course_id;
```

Here:

```text
Small Courses Table
        |
        v
Available to Mappers
        |
        v
Large Enrollment Table
        |
        v
Mapper performs join
```

### Interview answer

> A map-side join is useful when one table is small enough to be distributed to the mapper side. It avoids the expensive shuffle/reduce process for the join.

---

# 24. Map-Side vs Reduce-Side

Remember this table:

| Feature          | Map-Side Join             | Reduce-Side Join       |
| ---------------- | ------------------------- | ---------------------- |
| Small table      | Ideal                     | Not required           |
| Large table      | Yes                       | Yes                    |
| Shuffle          | Avoided/reduced           | Required               |
| Reducer for join | Not normally required     | Required               |
| Typical use      | Large fact + small lookup | Large + large datasets |
| Hive example     | `MAPJOIN`                 | Normal `JOIN`          |

### Simple corporate example

```text
Large table:
enrollments = 500 GB

Small table:
courses = 10 MB
```

Map-side join is suitable.

If both are huge:

```text
learners = 500 GB
enrollments = 1 TB
```

a normal distributed join is more appropriate.

## 25. Why Partition?

Our enrollment data contains:

```text
enrollment_year
```

We will partition by:

```text
enrollment_year
```

This means Hive can organize data like:

```text
enrollments/
|
+-- enrollment_year=2025/
|
+-- enrollment_year=2026/
|
+-- enrollment_year=2027/
```

---

# 26. Create Partitioned Table

Run:

```sql
CREATE TABLE enrollments (
    enrollment_id STRING,
    learner_id STRING,
    course_id STRING,
    enrollment_date STRING
)
PARTITIONED BY (
    enrollment_year INT
)
ROW FORMAT DELIMITED
FIELDS TERMINATED BY ','
STORED AS TEXTFILE;
```

Notice that:

```text
enrollment_year
```

is outside the normal columns.

It is the **partition column**.

---

# 27. Load Data into 2026 Partition

Run:

```sql
INSERT INTO TABLE enrollments
PARTITION (enrollment_year=2026)
SELECT
    enrollment_id,
    learner_id,
    course_id,
    enrollment_date
FROM enrollments_raw
WHERE enrollment_year=2026;
```

Check partitions:

```sql
SHOW PARTITIONS enrollments;
```

Expected:

```text
enrollment_year=2026
```

---

# 28. Query Partitioned Data

Run:

```sql
SELECT *
FROM enrollments
WHERE enrollment_year=2026;
```

This allows Hive to perform **partition pruning**.

Instead of considering every possible partition:

```text
2025
2026
2027
...
```

Hive can identify the required partition:

```text
2026
```

# 34. Managed vs External — Interview Explanation

| Feature                      | Managed/Internal                 | External           |
| ---------------------------- | -------------------------------- | ------------------ |
| Hive manages data            | Yes                              | No                 |
| Hive manages metadata        | Yes                              | Yes                |
| Data controlled outside Hive | Usually no                       | Yes                |
| Common use                   | Temporary/warehouse-managed data | Data lake/raw data |
| Example here                 | `learners`                       | `courses`          |

### Important interview question

**What happens when you drop a managed table?**

Generally, Hive removes:

```text
Table metadata
+
Table data
```

For an external table, dropping the table removes the Hive metadata while the underlying data is normally retained.

# 35. Partitioning — Interview Explanation

If the interviewer asks:

**Why did you partition the enrollment table?**

Answer:

> "Enrollment data can become very large over time. Since most analytical queries are performed for a particular year, I partitioned the table using enrollment_year. When a query specifies the partition column, Hive can use partition pruning and avoid scanning unrelated partitions."

---

# 36. Join Interview Explanation

If asked:

**Why did you use a map-side join?**

Answer:

> "The courses table is a small reference table compared with the potentially large enrollment table. A map-side join allows the small table to be made available to the mappers, reducing the expensive shuffle and reduce processing."

If asked:

**When would you use a reduce-side join?**

Answer:

> "When the tables being joined are both large and cannot practically be broadcast to the mapper side, Hive can perform the join using the distributed shuffle and reduce process."
