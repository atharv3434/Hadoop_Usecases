# Hive Use Case: Mobile App Activity Log Analytics

## 1. Problem Statement

A company operates a mobile application used by thousands of customers every day.

The application generates daily activity logs containing:

* User ID
* User name
* Event type
* Device type
* Event date
* Session duration

The data engineering team receives these log files every day and stores them in HDFS.

The company wants to use **Hive** to analyze the logs and generate reports such as:

* Which users generated application activity?
* How many users performed each type of event?
* What is the average session duration?
* How can user names be standardized before reporting?

For this project, we will create a **custom Hive UDF** that converts a user name into uppercase.

For example:

```text
rahul
```

becomes:

```text
RAHUL
```

The UDF will then be used directly inside a Hive query.

```text

Daily CSV Log
       |
       v
HDFS Raw Layer
       |
       v
Hive External Table
       |
       v

```

We use an **external Hive table** because the raw files are maintained in HDFS independently of Hive metadata.

### Short interview explanation

> "The application generates daily activity log files. The ingestion process places these files into an HDFS raw directory. Hive uses an external table to query the raw data without taking ownership of the underlying files. This allows the ingestion layer and Hive warehouse layer to remain loosely coupled."

# PART 2 — Create the Hive UDF

Now we implement the main requirement.

## 10. What is a Hive UDF?

UDF means:

**User Defined Function**

Hive already provides built-in functions such as:

```sql
UPPER()
LOWER()
LENGTH()
CONCAT()
```

But sometimes the business requires custom logic that is not available as a built-in Hive function.

We can write our own Java function and use it in Hive.

For this project:

```text
rahul
```

should become:

```text
RAHUL
```

Our function will be:

```text
to_upper()
```

---

# 11. Create Java UDF

Exit Hive:

```sql
EXIT;
```

Create a Java project directory:

```bash
mkdir -p ~/hive-app-logs/udf
```

Go there:

```bash
cd ~/hive-app-logs/udf
```

Create the Java file:

```bash
nano UpperCaseUDF.java
```

Enter:

```java
import org.apache.hadoop.hive.ql.exec.UDF;

public class UpperCaseUDF extends UDF {

    public String evaluate(String input) {

        if (input == null) {
            return null;
        }

        return input.toUpperCase();
    }
}
```

Save:

```text
Ctrl + O
Enter
Ctrl + X
```

# 21. Business Query Using UDF

Now let's make it more realistic.

> Generate a standardized activity report with uppercase user names and show users whose session duration is greater than 30 minutes.

```sql

    user_id,
    to_upper(user_name) AS standardized_user_name,
    event_type,
    device_type,
    session_minutes
```

# 22. Another Business Query

Find the total session time for each user.

```sql
SELECT
    to_upper(user_name) AS user_name,
    SUM(session_minutes) AS total_session_minutes
FROM app_activity
GROUP BY to_upper(user_name);
```

This demonstrates that the UDF can also participate in an analytical query.

# 24. Why External Table?

This is important for your interview.

We use:

```sql
CREATE EXTERNAL TABLE
```

because the raw logs are stored in HDFS and may be managed by the ingestion process independently of Hive.

If the Hive table is dropped:

```sql
DROP TABLE app_activity;
```

the external table's metadata is removed, while the underlying HDFS data is normally retained.

This is useful in a data-lake architecture.

---

# 25. Why Use a UDF?

Suppose the company has a business rule:

> All user names in reports must be standardized to uppercase.

Hive already has `UPPER()`, so **technically we would not need a custom UDF for this particular transformation in a real production system**.

For the lab, however, it is useful because it demonstrates the mechanism for creating a custom Hive UDF.

In a real project, a UDF would be justified when the business logic is more specialized, for example:

```text
Application-specific ID normalization
Custom code mapping
Organization-specific formatting
Special business rules
```

This is a good interview point: **don't claim you wrote a UDF when a standard Hive function already solves the problem.** Explain that this is a learning/demo UDF.
